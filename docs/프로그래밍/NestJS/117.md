NestJS는 테스트를 빌드하고 자동화하는데 필요한 아래와 같은 기능을 제공합니다.

- 단위 테스트 및 E2E 테스트 스캐폴드 제공
- 격리된 모듈 및 애플리케이션 로더를 빌드하는 테스트 러너 제공
- 테스트 도구에 종속되지 않고 Jest 및 Supertest 통합 기능 제공
- 종속성 주입 시스템을 이용한 쉬운 모킹 기능 제공

NestJS는 기본적으로 Jest를 사용하고 있어 Jest의 기능을 살펴보겠습니다.


## Config 속성


jest config 중 중요한 속성에 대해서 알아보겠습니다.


### coverageThreshold **[object]**[](https://jestjs.io/docs/configuration#coveragethreshold-object)


커버리지 결과에 대한 최소 임계값 적용을 구성하는데 사용합니다. 


임계값은 전역, 디렉토리, 파일 경로로 지정할 수 있습니다.


임계값이 충족되지 않으면 테스트가 실패합니다.


> 양수 임계값: 필요한 최소 백분율  
> 음수 임계값: 허용되는 실패 케이스의 최대 수


{% raw %}
```javascript
module.exports = {
  coverageThreshold: {
    global: {
      branches: 80,
      functions: 80,
      lines: 80,
      statements: -10,
    },
		'./src/components/': {
      branches: 40,
      statements: 40,
    },
    './src/reducers/**/*.js': {
      statements: 90,
    },
    './src/api/very-important-module.js': {
      branches: 100,
      functions: 100,
      lines: 100,
      statements: 100,
    },
  },
};
```
{% endraw %}


다음 구성을 사용하면 해당 경우에 테스트가 실패합니다.

- 전체 테스트 중 실패를 10개까지 허용하고, 전체 커버리지 80% 미만일 경우
- `./src/components` 폴더의 분기 또는 구문 커버리지가 40% 미만일 경우
- `./src/reducers/**/*.js` 패턴의 파일 중 한개라도 구문 커버리지가 90% 미만일 경우
- `./src/api/very-important-module.js` 파일 커버리지가 100% 미만일 경우

### moduleFileExtensions **[array<string>]**


모듈에서 사용하는 파일 확장자를 설정할 수 있습니다.


파일 확장자를 지정하지 않고 사용하는 경우 Jest는 배열 왼쪽으로 오른쪽 순서대로 설정한 확장자를 찾습니다.


따라서, 자주 사용하는 파일 확장자를 가장 왼쪽에 배치하는것이 좋습니다.


{% raw %}
```javascript
module.exports = {
  moduleFileExtensions: ['js', 'json', 'ts'],
};
```
{% endraw %}


### restoreMocks **[boolean]**


모든 테스트 전 모의 상태와 구현을 자동으로 복원합니다.


각 테스트 전에 `jest.restoreAllMocks()`를 호출하는 것과 동일합니다. (가짜 구현이 제거되고 원래 구현이 복원됩니다.)


### rootDir [string]


jest가 테스트와 모듈을 검색할 루트 폴더입니다. 기본값으로 jest 구성 파일이 포함된 폴더 경로 또는 package.json가 있는 경로로 지정됩니다.


### testMatch [array<string>]


jest가 테스트 파일을 감지하는 데 사용하는 글로브 패턴입니다.


{% raw %}
```javascript
module.exports = {
  rootDir: '.',
  testMatch: ['<rootDir>/src/**/*spec.ts'],
};
```
{% endraw %}


### collectCoverage [boolean]


테스트를 실행하는 동안 커버리지 정보를 수집할지 여부를 나타냅니다. (기본값 false)


## 테스트 전후 설정


beforeEach

- describe 기준으로 각 테스트 실행 전에 실행되는 함수

afterEach

- describe 기준으로 각 테스트 실행 후 실행되는 함수

beforeAll

- describe 기준으로 실행 전 가장 먼저 실행되는 함수

afterAll

- describe 기준으로 실행 후 가장 나중에 실행되는 함수

> beforeAll > beforeEach > afterEach > afterAll 순으로 동작


### 실행 순서

1. before*, after* 및 test를 제외한 코드 실행
2. beforeAll, beforeEach
3. test
4. afterEach
5. afterAll

`describe`가 중첩된 구조에서는 아래와 같이 동작합니다.


{% raw %}
```javascript
beforeAll(() => console.log('1 - beforeAll'));
afterAll(() => console.log('1 - afterAll'));
beforeEach(() => console.log('1 - beforeEach'));
afterEach(() => console.log('1 - afterEach'));

console.log('1 - describe outer-a');

test('', () => console.log('1 - test'));

console.log('1 - 1describe outer-b');

describe('Scoped / Nested block', () => {
	console.log('2 - describe outer-a');

  beforeAll(() => console.log('2 - beforeAll'));
  afterAll(() => console.log('2 - afterAll'));
  beforeEach(() => console.log('2 - beforeEach'));
  afterEach(() => console.log('2 - afterEach'));

	console.log('2 - describe outer-b');

  test('', () => console.log('2 - test'));

	console.log('2 - describe outer-c');
});

console.log('1 - 1describe outer-c');

// 1 - describe outer-a
// 1 - describe outer-b
// 2 - describe outer-a
// 2 - describe outer-b
// 2 - describe outer-c
// 1 - describe outer-c
// 1 - beforeAll
// 1 - beforeEach
// 1 - test
// 1 - afterEach
// 2 - beforeAll
// 1 - beforeEach
// 2 - beforeEach
// 2 - test
// 2 - afterEach
// 1 - afterEach
// 2 - afterAll
// 1 - afterAll
```
{% endraw %}

- 상태를 공유할 경우 다른 테스트 영향을 받아 테스트가 실패하는 경우가 존재합니다.
- 따라서 `beforeEach` 함수를 사용해서 테스트 실행 전 상태를 확인하는 것도 디버깅 중 한 가지 방법입니다.

## Mocking


Mocking이란 종속성을 제어하고 검사할 수 있는 객체로 대체하여 테스트 대상을 격리하는 기술로 다음 기능을 제공합니다.

- 함수 호출 감지
- 응답값 설정
- 구현 기능 변경

Jest에서 제공하는 Mocking 방법에 대해서 살펴보겠습니다.

- `jest.fn`: 함수를 mock
- `jest.mock`: 모듈을 mock
- `jest.spyOn`: 함수를 감시 또는 mock

위 방법들은 모두 mock 함수를 생성합니다.


각 함수들이 어떻게 동작하는지 살펴보겠습니다.


### jest.fn


Mocking을 위한 가장 기본적인 전략으로 함수를 모의 함수에 재할당하는 것입니다.


테스트 시 재할당된 함수가 사용되는 모든 곳에서 원래 함수 대신 모의 함수가 호출됩니다.


{% raw %}
```javascript
import * as app from "./app";
import * as math from "./math";

math.add = jest.fn();
math.subtract = jest.fn();

test("calls math.add", () => {
  app.doAdd(1, 2);
  expect(math.add).toHaveBeenCalledWith(1, 2);
});

test("calls math.subtract", () => {
  app.doSubtract(1, 2);
  expect(math.subtract).toHaveBeenCalledWith(1, 2);
});
```
{% endraw %}


이 방식은 다음의 이유로 잘 사용하지 않습니다.

- `jest.mock`은 모든 함수에 대해 자동으로 `jest.fn()` 작업을 수행
- `jest.spyOn`은 동일한 작업을 수행하지만 원래 함수로 복원 가능

### jest.mock


모듈 전체 함수를 모의 함수로 만들어 줍니다.


{% raw %}
```javascript
import * as app from "./app";
import * as math from "./math";

// Set all module functions to jest.fn
jest.mock("./math.js");

test("calls math.add", () => {
  app.doAdd(1, 2);
  expect(math.add).toHaveBeenCalledWith(1, 2);
});

test("calls math.subtract", () => {
  app.doSubtract(1, 2);
  expect(math.subtract).toHaveBeenCalledWith(1, 2);
});
```
{% endraw %}


위 방식의 유일한 단점은 모듈의 원래 구현에 접근하기 어렵다는 것입니다. 따라서, 원래 구현으로 되돌리기 위한 방법으로 `jest.spyOn`을 사용할 수 있습니다.


### jest.spyOn


경우에 따라서 함수가 호출되는 것만 보고 싶지만, 원래 구현은 그대로 유지해야 하는 경우가 있습니다. 또 다른 경우에는 구현을 모방하고 싶지만 나중에 다시 원래 구현으로 복원해야 할 때도 있습니다.


`jest.spyOn`을 사용하면 위의 경우를 모두 만족시킬 수 있습니다.


{% raw %}
```javascript
import * as app from "./app";
import * as math from "./math";

test("calls math.add", () => {
  const addMock = jest.spyOn(math, "add");

  // calls the original implementation
  expect(app.doAdd(1, 2)).toEqual(3);

  // and the spy stores the calls to add
  expect(addMock).toHaveBeenCalledWith(1, 2);

	// override the implementation
  addMock.mockImplementation(() => "mock");
  expect(app.doAdd(1, 2)).toEqual("mock");

  // restore the original implementation
  addMock.mockRestore();
  expect(app.doAdd(1, 2)).toEqual(3);
});
```
{% endraw %}


## Matchers


### Common


`toEqual`


객체 값이 같은지 체크하는 기능으로 객체 또는 배열의 모든 필드를 재귀적으로 확인합니다.


`undefined` 속성 및 배열 요소에 대해서는 키를 무시합니다. 보다 엄격한 검사를 원하면 `toStrictEqual`를 사용할 수 있습니다.


{% raw %}
```javascript
test('object assignment', () => {
  const data = {one: 1};
  data['two'] = 2;
  expect(data).toEqual({one: 1, two: 2});
});
```
{% endraw %}


### **Truthiness**


toBeNull: null 여부 체크


toBeUndefined: undefined 여부 체크


toBeDefined: toBeUndefined의 반대 여부 체크


toBeTruthy :참 여부 체크


toBeFalsy: 거짓 여부 체크


{% raw %}
```javascript
test('null', () => {
  const n = null;
  expect(n).toBeNull();
  expect(n).toBeDefined();
  expect(n).not.toBeUndefined();
  expect(n).not.toBeTruthy();
  expect(n).toBeFalsy();
});
```
{% endraw %}


### Numbers


{% raw %}
```javascript
test('two plus two', () => {
  const value = 2 + 2;
  expect(value).toBeGreaterThan(3);
  expect(value).toBeGreaterThanOrEqual(3.5);
  expect(value).toBeLessThan(5);
  expect(value).toBeLessThanOrEqual(4.5);

  // toBe and toEqual are equivalent for numbers
  expect(value).toBe(4);
  expect(value).toEqual(4);
});
```
{% endraw %}


부동소수점의 경우 [배정밀도 64비트 부동소수점](https://en.wikipedia.org/wiki/Double-precision_floating-point_format#:~:text=Double%2Dprecision%20floating%2Dpoint%20format%20(sometimes%20called%20FP64%20or,using%20a%20floating%20radix%20point.) 계산 방식에 의해 반올림 오류에 영향을 받지 않도록 toEqual 대신 toBeCloseTo 를 사용합니다.


{% raw %}
```javascript
test('adding floating point numbers', () => {
  const value = 0.1 + 0.2;
  //expect(value).toBe(0.3);           This won't work because of rounding error
  expect(value).toBeCloseTo(0.3); // This works.
});
```
{% endraw %}


### Strings


정규식을 사용해서 문자열을 확인할 수 있습니다.


{% raw %}
```javascript
test('there is no I in team', () => {
  expect('team').not.toMatch(/I/);
});

test('but there is a "stop" in Christoph', () => {
  expect('Christoph').toMatch(/stop/);
});
```
{% endraw %}


### Arrays and iterables


특정 항목에 포함되어 있는 요소를 확인할 수 있습니다.


{% raw %}
```javascript
const shoppingList = [
  'diapers',
  'kleenex',
  'trash bags',
  'paper towels',
  'milk',
];

test('the shopping list has milk on it', () => {
  expect(shoppingList).toContain('milk');
  expect(new Set(shoppingList)).toContain('milk');
});
```
{% endraw %}


### Exceptions


특정 함수가 호출 시 에러를 던지는지 테스트를 하려면 toThrow를 사용합니다.


{% raw %}
```javascript
function compileAndroidCode() {
  throw new Error('you are using the wrong JDK!');
}

test('compiling android goes as expected', () => {
  expect(() => compileAndroidCode()).toThrow();
  expect(() => compileAndroidCode()).toThrow(Error);

  // You can also use a string that must be contained in the error message or a regexp
  expect(() => compileAndroidCode()).toThrow('you are using the wrong JDK');
  expect(() => compileAndroidCode()).toThrow(/JDK/);

  // Or you can match an exact error message using a regexp like below
  expect(() => compileAndroidCode()).toThrow(/^you are using the wrong JDK$/); // Test fails
  expect(() => compileAndroidCode()).toThrow(/^you are using the wrong JDK!$/); // Test pass
});
```
{% endraw %}


## 테스팅 팁

- 전체 테스트가 실패했을 시 개별 테스트도 실패하는지 체크해 보아야 합니다.
- 특정 테스트만 실행시키는 방법은 `only` 를 추가하는 것입니다.

{% raw %}
```javascript
test.only('this will be the only test that runs', () => {
  expect(true).toBe(false);
});
```
{% endraw %}
